## 2024-05-24 - Do Not Leak Internal Server Errors

**Vulnerability:** Several API routes (`/api/library/[id]`, `/api/library`, and `/api/comics/[id]/progress`) were returning the raw error message (`err.message`) to the client when a `500 Internal Server Error` occurred.
**Learning:** Returning internal error messages to the client can expose sensitive details about the backend implementation, database queries, or underlying infrastructure. This information can be used by an attacker to further exploit the application. Error handling must always fail securely.
**Prevention:** Catch blocks should log the detailed error internally (`console.error`) for debugging purposes but return a generic error message (e.g., `{ error: 'Internal server error' }`) to the client. This ensures defense in depth by not revealing internals.## 2024-03-28 - Information Leakage in API Routes via Debug Logging
**Vulnerability:** API routes (`src/app/api/library/route.ts` and `src/app/api/bookmarks/route.ts`) were dumping raw session details, cookie previews, internal server variables (`NEXTAUTH_URL`, `AUTH_URL`), and internal database architectural warnings directly to `console.log` and `console.warn`, as well as directly into the JSON error responses (e.g., passing a generic `debug` object in a `401 Unauthorized` response).
**Learning:** Developers left highly verbose debugging logic active in production-bound API routes. This risks leaking sensitive authentication state (like session structure and cookie presence) to log management systems, and internally exposes architectural details to end users, violating the "Fail Securely" principle.
**Prevention:** Remove excessive `console.log` statements in API routes before committing, relying instead on `console.error` for strictly server-side error catching. Ensure API endpoints fail with generic messages (e.g., "Service unavailable") rather than specifying why it failed (e.g., "Database model not available") to avoid exposing internals.
